# Security Notes

Makocrypto is published under **Kerckhoffs's Principle**: every detail of
the algorithm is documented in [DESIGN.md](DESIGN.md) and visible in the
source code. The cipher's security is intended to rest entirely on the
secrecy of the key, not on hiding how it works. This document describes
what has and has not been verified, and is written to be read critically,
not as a marketing claim.

## What has been tested

### Avalanche effect

`tests/test_avalanche.c` measures, over 1000 random samples per
configuration, the percentage of ciphertext bits that change when:

- a single bit of the plaintext is flipped (key held fixed), and
- a single bit of the key is flipped (plaintext held fixed),

for both 128-bit and 256-bit keys. Representative measured results:

| Configuration                     | Bit difference |
|------------------------------------|----------------|
| Plaintext bit flip, 128-bit key    | ~50.17%        |
| Plaintext bit flip, 256-bit key    | ~50.16%        |
| Key bit flip, 128-bit key          | ~50.07%        |
| Key bit flip, 256-bit key          | ~49.85%        |

All four fall inside the 45-55% band the test asserts against an ideal
target of 50%, meeting the stated design goal that a single-bit change
propagates to roughly half of all output bits.

### Statistical randomness

`tools/randomness_check.c` runs three quick built-in checks over 1.6 MB of
ciphertext (counter-mode plaintext under a random key, isolating the
permutation itself):

- **Chi-square** goodness-of-fit against a uniform byte distribution
  (expected to land roughly in the 150-350 range for 255 degrees of
  freedom).
- **Shannon entropy** (expected close to the 8.0 bits/byte maximum).
- **Bit balance** (expected close to 50% ones).

These are coarse sanity checks, not a substitute for a formal statistical
test suite. `tools/nist_export.c` generates two 1 MB binary files (one
from the single-block permutation over counter plaintext, one from CBC
mode over random plaintext) formatted for direct input to the **NIST
Statistical Test Suite (SP 800-22)**. See [TESTING.md](TESTING.md) for how
to run it. The output of an actual NIST STS run should be included
alongside any claim that this cipher passes it -- this repository ships
the export tooling, not a completed run, since STS results should be
regenerated by whoever is evaluating a specific build.

### S-Box differential and linear properties (exhaustive)

`tools/sbox_analysis.c` computes the full Difference Distribution Table
(DDT) and Linear Approximation Table (LAT) for the S-Box, checking every
one of the 65536 possible (input difference, output difference) pairs and
every one of the 65025 possible nonzero (input mask, output mask) pairs --
not a sample, the complete table in both cases. Measured results:

| Metric                                    | Makocrypto | AES        |
|--------------------------------------------|------------|------------|
| Differential uniformity (max DDT entry)    | 4          | 4          |
| Max differential probability               | 4/256      | 4/256      |
| Max LAT bias                                | 16 (of 128)| 16 (of 128)|
| Linearity (2 x max bias)                    | 32/256     | 32/256     |

These numbers matching AES's exactly is not a coincidence and is not a
cherry-picked result: the affine transformation applied on top of the
GF(2^8) inverse (see [DESIGN.md](DESIGN.md#s-box-construction)) is a
bijective *linear* map composed with a constant XOR. Composing the
inverse function with any affine transformation preserves its
differential and linear properties exactly -- the affine layer only
changes *which* (difference, mask) pairs achieve the extremal values, not
the extremal values themselves. This is the same reason AES's own affine
step doesn't change the inverse function's DDT/LAT bounds either. The
practical takeaway is that Makocrypto's S-Box inherits AES's specific,
well-studied differential and linear resistance at the single-round
level, which is the strongest evidence in this document for the
structural argument below.

### Avalanche effect by round

`tools/avalanche_per_round.c` measures the bit-difference percentage
after *each* of the 16 rounds individually (not just the final
ciphertext), to see how quickly diffusion actually happens. Representative
measured results (128-bit key, single plaintext bit flipped):

| Round | Bit difference | Round | Bit difference |
|-------|-----------------|-------|-----------------|
| 0 (initial AddRoundKey only) | ~0.8% | 9  | ~50.0% |
| 1     | ~12.2%          | 10    | ~49.8% |
| 2     | ~50.3%          | 11    | ~50.3% |
| 3-8   | ~49.7-50.1%     | 12-16 | ~49.9-50.6% |

Diffusion converges to the ideal ~50% band by **round 2** and stays there
for the remaining 14 rounds. This means the 16-round count is not needed
for diffusion itself (2 rounds already achieve it) -- the extra rounds
exist to build a security margin against differential and linear
cryptanalysis, which depends on the number of rounds an attack has to
chain through, not on whether diffusion has "happened" in a bitwise
sense. This is the standard justification pattern for round counts in
SPN ciphers (diffusion converges fast; security margin against
statistical attacks is what determines how many additional rounds are
worth keeping) and is now backed by a measurement specific to this
cipher rather than only cited by analogy to AES.

The tool cross-checks its instrumented, per-round-capturing
reimplementation of the cipher against the real, shipped
`mako_encrypt_block()` on every run and refuses to report results if they
diverge, so these per-round numbers are not at risk of reflecting a
drifted or buggy reimplementation.

### Memory safety

The full test suite (`make test`, plus the CLI's encrypt/decrypt paths)
has been run under AddressSanitizer and UndefinedBehaviorSanitizer
(`make debug`) with zero reported issues: no buffer overflows,
out-of-bounds access, or undefined behavior detected in the cipher, key
schedule, CBC mode, KDF, or CLI code.

### Key schedule analysis

`tools/keyschedule_analysis.c` runs two checks, because the key schedule
is a common weak point in from-scratch ciphers even when the round
function itself is sound.

**Related-key avalanche** flips one bit of the master key and measures
what fraction of each individual round-key *word* changes, rather than
only looking at the final ciphertext. This surfaced a real, measurable
asymmetry, which is disclosed here rather than smoothed over:

For a 128-bit key, round-key words are generated in groups of four per
round. The first word in each group of four goes through `SubWord` +
`RotWord` + `RCON` (see [DESIGN.md](DESIGN.md#key-schedule)) and reaches
~50% related-key diffusion quickly. The other three words in each group
are derived by plain XOR with no S-Box step of their own, and converge
markedly slower and to a *lower ceiling*: in measurement, word positions
`4k+1` and `4k+2` settle around 37-41%, and `4k+3` settles around
28%, rather than all four converging to ~50% like the first word does.
This pattern is stable across both key sizes and is not a sampling
artifact -- it reflects the actual structure of the expansion formula in
`src/keyschedule.c`.

This is not a Makocrypto-specific bug: it is an inherited property of the
Rijndael-style key schedule this project deliberately follows (see
[DESIGN.md](DESIGN.md#key-schedule)), and the same asymmetry exists in
AES's own key schedule. It has been the subject of public cryptanalytic
attention before -- notably Biryukov and Khovratovich's 2009
related-key attacks on AES-192/256 exploit exactly this kind of structural
weakness in the schedule, as distinct from the round function. It has not
led to a practical break of AES in normal (non-related-key) use, which is
the threat model most deployments actually face, but it is a real,
disclosed limitation of this design rather than an invented one -- and
this project has not attempted to design around it (e.g. via
constructions like AES's own later successors sometimes use for
stronger key-schedule mixing).

**Round-key structural check** looks for the more directly exploitable
version of this concern: whether any two round-key words end up
identical or near-identical across many independently sampled keys
(`tools/keyschedule_analysis.c`'s Hamming-distance check), or whether any
pair of round-key words maintains a constant, key-independent XOR
relationship (which would mean one round key leaks another's value
without needing the key at all). Neither was found: the minimum observed
Hamming distance between any two distinct round-key words was well above
0, and 0 out of 2278 tested word pairs showed a constant offset across
200 independently sampled keys. The related-key asymmetry above is a
*rate-of-diffusion* concern, not a *key-independent leakage* concern --
that distinction matters and is why both checks are run separately.

### Known-plaintext attack simulation

`tools/known_plaintext_sim.c` asks a more practical question than the
structural arguments above: given many real (plaintext, ciphertext) pairs
under one fixed, unknown key, can an attacker actually pull out anything
useful?

- **Byte-level correlation**: across 20,000 known pairs, chi-square
  independence tests were run on every one of the 256 (plaintext byte
  position, ciphertext byte position) combinations. 2 out of 256 exceeded
  the 0.01-significance flag threshold, consistent with the false-positive
  rate expected from running 256 simultaneous tests (a handful of
  exceedances by chance is normal; this is why the check counts
  exceedances rather than treating any single one as damning).
- **Nearest-plaintext prediction**: for plaintexts differing from a known
  sample by 1-3 bits, the resulting ciphertext was on average 0.19 bits
  *closer* (out of 128 bits) to the known sample's ciphertext than a
  completely unrelated ciphertext was -- i.e., no measurable advantage.
  This confirms the avalanche effect actually holds in a realistic
  "attacker has seen similar plaintexts before" scenario, not only in the
  single-controlled-bit-flip test.
- **Reduced differential survival**: the S-Box's own best single-round
  differential (input difference `0x01` -> output difference `0x4F`,
  probability 4/256 per the DDT above) was carried through the *entire*
  16-round cipher and measured directly: the observed rate of the
  corresponding output-byte relationship was 384/100,000 (~0.98x the
  1/256 random baseline), meaning the single best differential available
  at the S-Box level provides no detectable advantage once it has to
  survive all 16 rounds.

None of these three checks found exploitable structure. Like the other
measurements in this document, they characterize this specific
implementation empirically; they are not a proof of security and do not
rule out attacks these particular tests were not designed to find (most
notably, none of this constitutes an actual key-recovery attack attempt,
which is a substantially larger undertaking than a distinguishing or
correlation test).

## What has not been verified

Being direct about this matters more than sounding confident:

- **No independent third-party cryptanalysis.** Makocrypto has not been
  reviewed by cryptographers outside this project. Every established
  cipher in wide use (AES, ChaCha20) has years of public analysis behind
  it; Makocrypto has none. Structural similarity to AES's design pattern
  is a reasonable design choice, but it is not equivalent to AES's actual
  track record.
- **No computed wide-trail security bound.** The S-Box's DDT/LAT are now
  exhaustively measured (see above), and the per-round avalanche and
  reduced-differential-survival measurements are direct experimental
  evidence rather than pure analogy. What is still missing is a formal
  wide-trail bound: a computed minimum number of active S-Boxes
  guaranteed by the specific MixColumns matrix and ShiftRows offsets used
  here, which would turn "the best S-Box-level differential doesn't
  survive 16 rounds in this measurement" into "no differential
  characteristic above probability X can exist for any N rounds,
  provably." That computation has not been done for Makocrypto's exact
  matrix and round count.
- **Side-channel resistance has not been evaluated.** In particular, the
  CBC padding validation in `mako_cbc_decrypt()` (`src/mode_cbc.c`)
  compares padding bytes with an early-exit loop, which is not
  constant-time. A timing side channel here could, in principle, assist a
  padding-oracle-style attack in a scenario where an attacker can
  repeatedly submit modified ciphertexts and observe response timing.
  Table lookups in `mix_columns`/`inv_mix_columns` (`src/gf256.h`) are
  also not guaranteed constant-time on all hardware, since table-lookup
  timing can depend on cache state. Neither the KDF, the key schedule,
  nor the core encrypt/decrypt path have been audited for timing or
  cache-based side channels.
- **No practical related-key attack has been attempted.** The key
  schedule's slower-converging round-key words (documented above under
  "Key schedule analysis") are a measured *rate* asymmetry, not a
  demonstrated attack. Whether this asymmetry is actually exploitable
  into a related-key distinguisher or key-recovery attack -- the kind of
  result Biryukov and Khovratovich produced against full AES-192/256 --
  has not been attempted against Makocrypto specifically. Related-key
  attacks also require a threat model where an attacker can obtain
  ciphertexts under multiple related keys, which does not apply to
  Makocrypto's CBC file-encryption use case (a single key is used per
  file, not attacker-chosen related keys), but would matter if this
  cipher were repurposed into a different construction (e.g. a hash
  function) that exposes the key schedule more directly.
- **No authentication.** CBC mode provides confidentiality only. It does
  not detect tampering beyond the coarse padding-validity check (which is
  not a substitute for a MAC). Anyone deploying this for real data should
  pair it with a separate MAC (encrypt-then-MAC) or use an AEAD
  construction instead -- this is exactly the reasoning that led to
  standards like AES-GCM.

## Recommendation

Makocrypto is a learning and portfolio project demonstrating cipher
design, implementation, and testing methodology. For anything where real
data confidentiality matters, use a standardized, widely reviewed
primitive (AES-256-GCM, ChaCha20-Poly1305) via a maintained library rather
than this or any other from-scratch cipher. The value of this project is
in the design and testing process it demonstrates, not as a
production-ready alternative to those primitives.
