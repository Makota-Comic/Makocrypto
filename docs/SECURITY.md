# Security Notes

I'm publishing Makocrypto under **Kerckhoffs's Principle**: every detail
of the algorithm is documented in [DESIGN.md](DESIGN.md) and visible in
the source code. The cipher's security is supposed to rest entirely on
the secrecy of the key, not on hiding how it works. This document is my
honest account of what I have and haven't verified -- read it critically,
not as a marketing claim.

## What I've tested

### Avalanche effect

`tests/test_avalanche.c` measures, over 1000 random samples per
configuration, the percentage of ciphertext bits that change when:

- a single bit of the plaintext is flipped (key held fixed), and
- a single bit of the key is flipped (plaintext held fixed),

for both 128-bit and 256-bit keys. Here's what I measured:

| Configuration                     | Bit difference |
|------------------------------------|----------------|
| Plaintext bit flip, 128-bit key    | ~50.17%        |
| Plaintext bit flip, 256-bit key    | ~50.16%        |
| Key bit flip, 128-bit key          | ~50.07%        |
| Key bit flip, 256-bit key          | ~49.85%        |

All four land inside the 45-55% band my test asserts against an ideal
target of 50%, which is exactly what I wanted: a single-bit change should
propagate to roughly half of all output bits.

### Statistical randomness

`tools/randomness_check.c` runs three quick built-in checks over 1.6 MB
of ciphertext (counter-mode plaintext under a random key, so I'm
isolating the permutation itself):

- **Chi-square** goodness-of-fit against a uniform byte distribution
  (I expect this to land roughly in the 150-350 range for 255 degrees of
  freedom).
- **Shannon entropy** (should be close to the 8.0 bits/byte maximum).
- **Bit balance** (should be close to 50% ones).

These are just coarse sanity checks -- not a substitute for a real
statistical test suite. `tools/nist_export.c` generates two 1 MB binary
files (one from the single-block permutation over counter plaintext, one
from CBC mode over random plaintext) formatted for direct input to the
**NIST Statistical Test Suite (SP 800-22)**. See [TESTING.md](TESTING.md)
for how to run it. If you're going to claim this cipher passes NIST STS,
you should include the actual output of a run alongside that claim --
this repo ships the export tooling, not a completed run, since I think
STS results should get regenerated by whoever's evaluating a specific
build, not taken on my word.

### S-Box differential and linear properties (exhaustive)

`tools/sbox_analysis.c` computes the full Difference Distribution Table
(DDT) and Linear Approximation Table (LAT) for the S-Box, checking every
one of the 65536 possible (input difference, output difference) pairs and
every one of the 65025 possible nonzero (input mask, output mask) pairs --
not a sample, the complete table both times. Here's what I got:

| Metric                                    | Makocrypto | AES        |
|--------------------------------------------|------------|------------|
| Differential uniformity (max DDT entry)    | 4          | 4          |
| Max differential probability               | 4/256      | 4/256      |
| Max LAT bias                                | 16 (of 128)| 16 (of 128)|
| Linearity (2 x max bias)                    | 32/256     | 32/256     |

These numbers matching AES's exactly isn't a coincidence, and I didn't
cherry-pick it: the affine transformation I applied on top of the
GF(2^8) inverse (see [DESIGN.md](DESIGN.md#s-box-construction)) is a
bijective *linear* map composed with a constant XOR. Composing the
inverse function with any affine transformation preserves its
differential and linear properties exactly -- the affine layer only
changes *which* (difference, mask) pairs achieve the extremal values, not
the extremal values themselves. That's the same reason AES's own affine
step doesn't change the inverse function's DDT/LAT bounds either. What
this means in practice: my S-Box inherits AES's specific, well-studied
differential and linear resistance at the single-round level, which is
the strongest evidence I have in this document for the structural
argument below.

### Avalanche effect by round

`tools/avalanche_per_round.c` measures the bit-difference percentage
after *each* of the 16 rounds individually (not just the final
ciphertext), so I can see how quickly diffusion actually happens. Here's
what I measured (128-bit key, single plaintext bit flipped):

| Round | Bit difference | Round | Bit difference |
|-------|-----------------|-------|-----------------|
| 0 (initial AddRoundKey only) | ~0.8% | 9  | ~50.0% |
| 1     | ~12.2%          | 10    | ~49.8% |
| 2     | ~50.3%          | 11    | ~50.3% |
| 3-8   | ~49.7-50.1%     | 12-16 | ~49.9-50.6% |

Diffusion converges to the ideal ~50% band by **round 2** and stays there
for the remaining 14 rounds. So the 16-round count isn't there for
diffusion itself -- 2 rounds already get you there. The extra rounds
exist to build a security margin against differential and linear
cryptanalysis, which depends on how many rounds an attack has to chain
through, not on whether diffusion has "happened" in a bitwise sense.
This is the standard justification pattern for round counts in SPN
ciphers (diffusion converges fast; security margin against statistical
attacks is what determines how many extra rounds are worth keeping), and
now I've got a measurement specific to this cipher backing it up, rather
than just citing AES by analogy.

The tool cross-checks its instrumented, per-round-capturing
reimplementation of the cipher against the real, shipped
`mako_encrypt_block()` on every run and refuses to report results if they
diverge, so I'm confident these per-round numbers aren't reflecting a
drifted or buggy reimplementation.

### Memory safety

I've run the full test suite (`make test`, plus the CLI's encrypt/decrypt
paths) under AddressSanitizer and UndefinedBehaviorSanitizer (`make
debug`) with zero reported issues: no buffer overflows, out-of-bounds
access, or undefined behavior in the cipher, key schedule, CBC mode, KDF,
or CLI code.

### Key schedule analysis

`tools/keyschedule_analysis.c` runs two checks, because the key schedule
is a common weak point in from-scratch ciphers even when the round
function itself is sound.

**Related-key avalanche** flips one bit of the master key and measures
what fraction of each individual round-key *word* changes, rather than
only looking at the final ciphertext. This surfaced a real, measurable
asymmetry, and I'm disclosing it here rather than smoothing it over:

For a 128-bit key, round-key words get generated in groups of four per
round. The first word in each group of four goes through `SubWord` +
`RotWord` + `RCON` (see [DESIGN.md](DESIGN.md#key-schedule)) and reaches
~50% related-key diffusion quickly. The other three words in each group
are derived by plain XOR with no S-Box step of their own, and converge
markedly slower and to a *lower ceiling*: in my measurements, word
positions `4k+1` and `4k+2` settle around 37-41%, and `4k+3` settles
around 28%, rather than all four converging to ~50% like the first word
does. This pattern is stable across both key sizes and isn't a sampling
artifact -- it reflects the actual structure of the expansion formula in
`src/keyschedule.c`.

This isn't a Makocrypto-specific bug: it's an inherited property of the
Rijndael-style key schedule I deliberately followed (see
[DESIGN.md](DESIGN.md#key-schedule)), and the same asymmetry exists in
AES's own key schedule. It's actually gotten public cryptanalytic
attention before -- Biryukov and Khovratovich's 2009 related-key attacks
on AES-192/256 exploit exactly this kind of structural weakness in the
schedule, as distinct from the round function. It hasn't led to a
practical break of AES in normal (non-related-key) use, which is the
threat model most deployments actually face, but it's a real, disclosed
limitation of this design rather than one I'm inventing -- and I haven't
tried to design around it (the way some of AES's later successors use
stronger key-schedule mixing).

**Round-key structural check** looks for the more directly exploitable
version of this concern: whether any two round-key words end up
identical or near-identical across many independently sampled keys
(`tools/keyschedule_analysis.c`'s Hamming-distance check), or whether any
pair of round-key words maintains a constant, key-independent XOR
relationship (which would mean one round key leaks another's value
without needing the key at all). I didn't find either: the minimum
observed Hamming distance between any two distinct round-key words was
well above 0, and 0 out of 2278 tested word pairs showed a constant
offset across 200 independently sampled keys. The related-key asymmetry
above is a *rate-of-diffusion* concern, not a *key-independent leakage*
concern -- that distinction matters, which is why I run both checks
separately.

### Known-plaintext attack simulation

`tools/known_plaintext_sim.c` asks a more practical question than the
structural arguments above: given many real (plaintext, ciphertext)
pairs under one fixed, unknown key, can an attacker actually pull out
anything useful?

- **Byte-level correlation**: across 20,000 known pairs, I ran
  chi-square independence tests on every one of the 256 (plaintext byte
  position, ciphertext byte position) combinations. 2 out of 256
  exceeded the 0.01-significance flag threshold, which is consistent
  with the false-positive rate you'd expect from running 256
  simultaneous tests (a handful of exceedances by chance is normal --
  that's why I count exceedances instead of treating any single one as
  damning).
- **Nearest-plaintext prediction**: for plaintexts differing from a
  known sample by 1-3 bits, the resulting ciphertext was on average 0.19
  bits *closer* (out of 128 bits) to the known sample's ciphertext than
  a completely unrelated ciphertext was -- basically no measurable
  advantage. This confirms the avalanche effect actually holds in a
  realistic "attacker has seen similar plaintexts before" scenario, not
  only in the single-controlled-bit-flip test.
- **Reduced differential survival**: I took the S-Box's own best
  single-round differential (input difference `0x01` -> output
  difference `0x4F`, probability 4/256 per the DDT above) and carried it
  through the *entire* 16-round cipher, measuring directly: the observed
  rate of the corresponding output-byte relationship was 384/100,000
  (~0.98x the 1/256 random baseline), meaning the single best
  differential available at the S-Box level gives you no detectable
  advantage once it has to survive all 16 rounds.

None of these three checks found exploitable structure. Like the other
measurements in this doc, they characterize this specific implementation
empirically -- they're not a proof of security and don't rule out
attacks these particular tests weren't designed to find (most notably,
none of this is an actual key-recovery attack attempt, which is a
substantially bigger undertaking than a distinguishing or correlation
test).

### Differential trail search

`tools/differential_trail_search.c` runs a Matsui-style branch-and-bound
search for the highest-probability differential trail through a reduced
number of rounds (up to 4, using the exhaustive per-difference best DDT
probability from the S-Box analysis above to prune branches), then I
extrapolate to the full 16 rounds using the standard wide-trail
argument. Here's what I measured for the reduced rounds (128-bit key
structure, byte-level model):

| Rounds | Best trail probability (log2) |
|--------|-------------------------------|
| 1      | 2^-6 (single active S-box)     |
| 2      | 2^-30                          |
| 3      | 2^-126                         |
| 4      | 2^-222                         |

Extrapolating via the wide-trail bound (this MixColumns matrix has
branch number 5, identical to AES's, which guarantees at least 5 active
S-boxes per 2 consecutive rounds once any byte differs; combined with
the S-Box's own measured best single-round probability of 4/256): the
full 16 rounds give a minimum of `floor(16/2) * 5 = 40` active S-boxes,
bounding any 16-round differential characteristic's probability at or
below `2^-240`. That's far below both `2^-128` (128-bit brute-force
search) and `2^-256` (256-bit), meaning no differential characteristic
spanning all 16 rounds can be more efficient than brute-force key
search.

**Important caveat, and I want to be upfront about this rather than
gloss over it**: this search assumes each active byte independently
achieves its own best DDT probability every round. In reality, once
MixColumns has linked specific byte difference values together, they
can't all simultaneously realize their individually-best DDT output on
every later round -- the true trail probability is linked to the exact
values, not just which bytes are active. So the numbers above are an
**upper bound** on the true best-trail probability, not an exact figure.
That's the safe direction for a security argument (the true probability
can only be lower, so a bound already below brute-force-search
probability stays valid), but don't read it as a precise
trail-probability calculation -- and the same shortcut wouldn't be valid
if I were trying to claim a trail *is* exploitable.

### Impossible differential search

`tools/impossible_differential_search.c` runs an automated
miss-in-the-middle search for single-active-byte-in/single-active-byte-
out impossible (truncated) differentials, propagating a starting pattern
forward and a target pattern backward and checking for a provable
contradiction (a byte position where one direction guarantees "active"
and the other guarantees "inactive"). This is the same search form that
found the historically significant Biham-Keller (2000) 4-round AES
impossible differential.

Here's what I found: for every total round count I tested (2 through
10), splits where one side is exactly 1 round contradict for all 256
tested position pairs; splits where both sides are 2 or more rounds
contradict for none of the 256 pairs. This pattern is a direct
consequence of the truncated model's own mechanics (a 1-round side still
has provably inactive bytes; a 2+-round side has already reached full
diffusion, matching the round-2 avalanche convergence I measured above)
rather than a round-count-limited result the way AES's specific 4-round
bound is. This tool's development process is itself instructive, and I
left it visible in the tool's own output: an earlier draft of mine
mischaracterized the imbalanced-split result as a coarse-model artifact
before I checked the published literature, when it's actually the
historically meaningful form -- the corrected reasoning, and the
literature comparison behind it, is documented directly in the tool's
printed output.

What this confirms is that Makocrypto has the same *kind* of
single-active-byte impossible differential AES does, at the same shape.
Pinning down exactly where Makocrypto's analogous limit falls (the way
AES's is known to be 4 rounds specifically) would need modeling exact
difference values through the 1-round side rather than only
active/inactive status -- a materially harder search I haven't
implemented. I also haven't attempted the practically important
question -- whether a found impossible differential extends, via
key-guessing rounds on each side, far enough to threaten the *full*
cipher; for reference, the best published impossible-differential
key-recovery attacks against AES-128 (10 rounds) reach 7 rounds, not all
10, and Makocrypto's 16 rounds gives more headroom by the same
structural reasoning I've used throughout this doc, though that's a
structural comparison, not a computed attack-complexity figure for
Makocrypto specifically.

### Integral (Square) attack test

`tools/integral_attack_test.c` runs the classic Square/integral test:
encrypts a full 256-plaintext lambda set (one byte sweeping all 256
values, others fixed) through a reduced number of real cipher rounds,
and checks whether the XOR-sum of all 256 resulting ciphertexts is
balanced (zero) at each byte position -- the property Square/integral
attacks exploit for key recovery. Here's what I measured (worst-case
active byte per round, 128-bit key):

| Rounds | Balanced byte positions | 
|--------|--------------------------|
| 1      | 16 / 16 (fully balanced) |
| 2      | 16 / 16 (fully balanced) |
| 3      | 16 / 16 (fully balanced) |
| 4      | 0 / 16                   |
| 5      | 0 / 16                   |
| 6      | 0 / 16                   |

The balanced property holds exactly through round 3 and disappears
completely from round 4 onward (I verified it stays stable through
round 8 in extended testing), matching published AES results precisely:
the classic Square/integral property is well-documented to hold for
exactly 3 rounds of AES (which makes sense, since Square, AES's direct
ancestor cipher, is literally named for this property and attack).
Published integral attacks against AES-128 reach 6 of its 10 rounds at
best, using additional key-guessing rounds layered on top of the core
3-4 round balanced property; Makocrypto's 16 rounds gives considerably
more headroom by the same reasoning.

This test only covers the classic single-active-byte lambda-set form,
not higher-order integral distinguishers built from multiple active
bytes (which the literature also uses to extend integral attacks
further), and I haven't implemented the key-recovery extension rounds
needed to turn the observed balanced-property boundary into an actual
attack-round count for Makocrypto specifically.

### Timing side-channel measurement

`tools/timing_sidechannel_test.c` measures whether `mako_cbc_decrypt()`'s
padding validation loop (`src/mode_cbc.c`) -- already disclosed above as
not constant-time in source-code terms, since it returns as soon as it
finds the first mismatching padding byte -- produces an actually
measurable timing difference an attacker could exploit as a
padding-oracle side channel (Vaudenay 2002). It uses a Welch's t-test
(the same statistical approach TVLA-style timing leakage methodology
uses) comparing decryption time for correctly-padded ciphertext against
padding corrupted at various depths, with `|t| > 4.5` as the
conventional significance threshold.

**I've deliberately not run this tool to produce a trusted result in my
own development environment.** That environment is a shared, virtualized
sandbox with substantial scheduling noise; a smoke test I ran confirmed
standard deviations in the 1000+ nanosecond range against mean timings
of only ~2000-2300 nanoseconds -- i.e. noise on the same order as the
total measurement itself, which is exactly the condition where this kind
of test can't distinguish a genuine timing signal from environmental
jitter in either direction. Reporting a "no signal found" result from
that environment would be actively misleading, not reassuring, so I'm
not claiming one.

To get a trustworthy measurement, run this on a dedicated, idle physical
machine (not a VM, container, or shared cloud instance), ideally with the
process pinned to an isolated CPU core and CPU frequency scaling
disabled, repeated across multiple runs for consistency, and ideally
validated against a known-constant-time reference implementation first
to confirm the methodology can actually detect a signal of the expected
size. The tool itself prints full instructions
(`./build/bin/timing_sidechannel_test`), and I'm not duplicating them
here so the two copies don't drift out of sync.

## What I haven't verified

Being direct about this matters more to me than sounding confident:

- **No independent third-party cryptanalysis.** Nobody outside this
  project has reviewed Makocrypto. Every established cipher in wide use
  (AES, ChaCha20) has years of public analysis behind it; Makocrypto has
  none. Following AES's design pattern structurally is a reasonable
  choice on my part, but it's not equivalent to AES's actual track
  record.
- **No exact (non-bounded) wide-trail security proof.** I've
  exhaustively measured the S-Box's DDT/LAT, and
  `tools/differential_trail_search.c` gives me a direct reduced-round
  (up to 4 rounds) branch-and-bound search result, extrapolated to 16
  rounds via the standard wide-trail argument. That's meaningfully
  stronger evidence than pure analogy to AES, but the search itself
  discloses an important limitation: it computes an upper bound assuming
  each active byte independently achieves its own best DDT probability
  every round, not the exact achievable trail probability (real byte
  values are linked through MixColumns in ways the search doesn't
  track). The bound is on the safe side for a security argument (true
  probability can only be lower), but I haven't done a tight, exact
  computation for this specific matrix and round count.
- **Side-channel resistance hasn't been conclusively evaluated.**
  `tools/timing_sidechannel_test.c` exists specifically to measure the
  CBC padding validation's known non-constant-time behavior
  (`mako_cbc_decrypt()` in `src/mode_cbc.c`, which returns as soon as it
  finds the first mismatching padding byte), but I've deliberately not
  run it to produce a trusted result in my own development environment
  (a shared, virtualized sandbox with scheduling noise on the same order
  as the timings being measured -- see "Timing side-channel measurement"
  above for the smoke-test numbers that confirm this). Whether the
  theoretical timing leak is practically exploitable is therefore still
  an open question pending a measurement on dedicated hardware, not a
  settled negative or positive result. Table lookups in
  `mix_columns`/`inv_mix_columns` (`src/gf256.h`) also aren't guaranteed
  constant-time on all hardware, since table-lookup timing can depend on
  cache state, and I haven't measured that at all. Neither the KDF nor
  the key schedule have been audited for timing or cache-based side
  channels.
- **No practical related-key attack has been attempted.** The key
  schedule's slower-converging round-key words (documented above under
  "Key schedule analysis") are a measured *rate* asymmetry, not a
  demonstrated attack. Whether this asymmetry is actually exploitable
  into a related-key distinguisher or key-recovery attack -- the kind of
  result Biryukov and Khovratovich produced against full AES-192/256 --
  is something I haven't attempted against Makocrypto specifically.
  Related-key attacks also need a threat model where an attacker can get
  ciphertexts under multiple related keys, which doesn't apply to
  Makocrypto's CBC file-encryption use case (a single key is used per
  file, not attacker-chosen related keys), but it would matter if I ever
  repurposed this cipher into a different construction (e.g. a hash
  function) that exposes the key schedule more directly.
- **No key-recovery extension for the found impossible differential or
  integral property.** Both `tools/impossible_differential_search.c` and
  `tools/integral_attack_test.c` confirm Makocrypto has the same *kind*
  of reduced-round structural property AES has (a single-active-byte
  impossible differential of matching shape; a balanced integral
  property through exactly 3 rounds). Neither tool implements the
  key-guessing extension rounds that turn these reduced-round properties
  into an actual attack against additional rounds in practice (the way
  published attacks extend AES's core 3-4 round properties to attack 6-7
  of AES-128's 10 rounds). I haven't attempted to establish an analogous
  attacked-round-count for Makocrypto specifically.
- **CBC mode (format version 1) only gives you confidentiality, and I'm
  keeping it read-only for backward compatibility.** I originally had
  this listed as an open limitation here ("no authentication... pair it
  with a separate MAC... or use an AEAD construction instead"). I've
  since fixed it: `mako_gcm_encrypt()`/`mako_gcm_decrypt()`
  (`src/mode_gcm.c`) implement a GCM-style AEAD construction (CTR-mode
  encryption plus a GHASH-based Carter-Wegman MAC) on top of the same
  block cipher, and that's what the `makocrypto` CLI now uses for all
  new encryption (file format version 2 -- see "File format" in
  [DESIGN.md](DESIGN.md)). The two concrete problems the old CBC-only
  design had are both closed by this:
  - **The padding-oracle side channel is gone from the write path.**
    `mode_cbc.c`'s `mako_cbc_decrypt()` still exists, still returns a
    distinct `MAKO_ERR_PADDING` status, and its padding-check loop is
    still not constant-time (see `tools/timing_sidechannel_test.c`) --
    none of that changed, and none of it needs to, because it's now only
    ever reached when reading a pre-existing version-1 file. The CLI's
    error reporting (`src/main.c`) doesn't distinguish
    `MAKO_ERR_PADDING` from any other decryption failure in what it
    prints, for either format version, so there's no externally
    observable difference between "bad padding," "bad auth tag," "wrong
    passphrase," or "wrong key size" -- all four internal failure modes
    collapse to one generic message. A deployment that only ever writes
    and reads version-2 files never touches the CBC decrypt path at all.
  - **Ciphertext and header tampering are now detected.** GCM's tag
    covers both the ciphertext and, via the CLI's use of associated
    data, the file header fields themselves (magic, version, key-size
    flag, salt, nonce) -- flipping any bit anywhere in the file causes
    `mako_gcm_decrypt()` to return `MAKO_ERR_AUTH_FAILED` before any
    plaintext is released, instead of silently producing corrupted
    plaintext (which is what CBC-without-a-MAC does for tampering that
    doesn't happen to land in the final block's padding).

  What hasn't changed, and I want to be precise about this: this is
  still a hand-rolled AEAD construction over a hand-rolled block cipher,
  not a drop-in use of a standardized, widely-reviewed AES-GCM
  implementation. I've checked `mako_gcm_encrypt()`/`decrypt()`'s
  GHASH/CTR plumbing against the published NIST/McGrew-Viega GCM test
  vectors (empty input, single-block, multi-block-with-partial-final-
  block, with and without associated data) using a separately-written
  reference AES-128 purely to supply known-correct block cipher outputs
  for that check -- this validates that the GCM *construction* is wired
  correctly, but it says nothing about the security of the underlying
  Makocrypto cipher itself, which is exactly the open question the rest
  of this doc (differential/linear/impossible-differential/integral
  analysis) is already about. An AEAD wrapper can't be stronger than the
  block cipher it wraps; see "Recommendation" below, which applies the
  same way before and after this change.
- **The KDF now takes a per-file salt; it previously didn't.** Before
  this change, `mako_kdf_derive()` only took a passphrase, which meant
  the same passphrase always derived the same key regardless of which
  file it was used on -- letting an attacker precompute a dictionary of
  passphrase-to-key derivations once and reuse it against every
  Makocrypto file they came across, instead of having to redo the
  (deliberately expensive, `MAKO_KDF_ITERATIONS`-stretched) derivation
  per file. `mako_kdf_derive()` now requires a `MAKO_KDF_SALT_SIZE` (16)
  byte salt, mixed into the very first absorption step rather than
  applied as a shallow post-processing XOR, and the CLI generates a
  fresh random salt per file (stored in the version-2 header, alongside
  the GCM nonce). This doesn't change anything about the KDF's
  underlying construction (Davies-Meyer compression over the Makocrypto
  block cipher, see `src/kdf.c`) or its resistance to brute force for a
  *given* salt -- only whether the same work can get reused across
  files, which now it can't.

## Recommendation

Makocrypto is a learning and portfolio project for me, demonstrating
cipher design, implementation, and testing methodology. File format
version 2 (GCM, salted KDF) closes the specific mode-of-operation
mistakes (padding oracle, no integrity check, unsalted KDF) that version
1 had -- but that's a statement about the *mode of operation* being
sound, not about the underlying block cipher having received the years
of public cryptanalysis that AES or ChaCha20 have. If you're working
with anything where real data confidentiality matters, use a
standardized, widely reviewed primitive (AES-256-GCM, ChaCha20-Poly1305)
via a maintained library instead of this or any other from-scratch
cipher. The value I see in this project is in the design and testing
process it demonstrates, not as a production-ready alternative to those
primitives.
